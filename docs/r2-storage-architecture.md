# Life OS — Cloudflare R2 Storage Architecture

**Status: DESIGN ONLY. No bucket exists. No credentials have been created.**
**Created 2026-07-31.**

> **Today the app has no file capability at all** — no file picker, no image
> embedding, no object storage. This document designs that capability from
> scratch, so Project documents and Library attachments become possible.

---

## 1. Division of responsibility

| Stores | Where |
|---|---|
| **Structured records** (tasks, projects, pages, metadata) | **PostgreSQL** |
| **Binary blobs** (images, documents, video, audio, exports) | **Cloudflare R2** |

**Rule: R2 is never the primary database.** Life OS records are never stored as
loose JSON objects in R2 as the source of truth. For every object in R2 there is
a row in `attachments` holding the object key, size, type, checksum and owner.
If a row does not exist, the object is an orphan and is cleaned up.

**Why R2 fits:** S3-compatible, **zero egress fees** (important for
image/video-heavy Library content), and cheap at rest.

---

## 2. Buckets

Three buckets, all **private**, no public access, no public dev URL:

| Bucket | Contents | Lifecycle |
|---|---|---|
| `life-os-prod` | user attachments | keep; delete 30 days after soft-delete |
| `life-os-exports` | user-generated export bundles | **auto-delete after 7 days** |
| `life-os-backups` | database dumps + Firestore snapshots | 7 daily / 4 weekly / 6 monthly |

Separate buckets (rather than prefixes) so **retention rules cannot collide** —
a lifecycle policy that expires exports must never touch backups. Staging uses
its own `life-os-staging-*` buckets.

## 3. Object key convention

```
users/{userId}/profiles/{profileId}/attachments/{attachmentId}/{safeFileName}
users/{userId}/profiles/{profileId}/thumbnails/{attachmentId}/{size}.webp
users/{userId}/profiles/{profileId}/exports/{exportId}/life-os-export.zip
backups/postgres/{YYYY}/{MM}/{DD}/life-os-{timestamp}.dump
backups/firestore/{YYYY}/{MM}/{DD}/profile-{profileId}.json
```

Properties that matter:
- **Ownership is visible in the path**, so a mis-scoped key is obvious in logs
  and audits.
- **`{attachmentId}` before the filename** guarantees uniqueness — two files
  called `notes.pdf` never collide, and the original name is preserved for
  download.
- **`safeFileName`** is sanitised server-side: Unicode-normalised, path
  separators and control characters stripped, length-capped (~120 chars), and a
  fallback of `file` if nothing survives. The *original* name is kept in
  Postgres, not in the key.
- Keys are **generated by the backend only** — never accepted from the client.

## 4. Upload flow (signed, direct-to-R2)

The file never passes through the Railway backend — that keeps the API cheap and
fast — but the backend still controls **every decision**.

```
1. Client  → POST /api/v1/profiles/:id/attachments:presign-upload
             { filename, contentType, byteSize, checksumSha256, entityType, entityId }

2. Backend   verifies the Firebase token
             verifies profile ownership
             validates content type + size against policy
             checks the checksum for an existing identical file (dedup)
             INSERTs attachments row with status='pending'
             generates the object key
             returns a SIGNED PUT URL (15-minute TTL)

3. Client  → PUT the bytes directly to R2 using that URL

4. Client  → POST /api/v1/profiles/:id/attachments/:attachmentId:complete

5. Backend   HEADs the object: confirms it exists, size matches, type matches
             flips status to 'ready'
             queues thumbnail generation for images
```

**Why a two-step confirm:** an upload that is started and abandoned leaves a
`pending` row and possibly a stray object. The reconciliation job (§10) cleans
both. Without step 4 there is no reliable way to know an upload finished.

**The browser never receives permanent R2 credentials.** Only short-lived,
single-object, single-method signed URLs.

---

## 5. Download flow

```
Client → POST /api/v1/profiles/:id/attachments/:attachmentId:presign-download
Backend  verify token → verify ownership → verify status='ready'
         → return a signed GET URL, 5-minute TTL
Client → GET the object directly from R2
```

- Short TTL because a signed URL is a bearer token — anyone holding it can read
  the object until it expires.
- Signed URLs are **never logged** and never embedded in exported HTML.
- For inline images in the Library, the client requests URLs on render and
  refreshes them as needed. If that proves noisy, the alternative is a backend
  streaming proxy (`GET /attachments/:id/raw`) — simpler and fully private, at
  the cost of bandwidth through Railway. **Start with signed URLs.**

## 6. Limits and allowed types

| Category | Max size | Types |
|---|---|---|
| Image | 25 MB | `image/jpeg`, `png`, `webp`, `gif`, `heic`, `avif` |
| Document | 50 MB | `application/pdf`, plain text, markdown, csv, docx, xlsx, pptx |
| Audio | 100 MB | `audio/mpeg`, `mp4`, `wav`, `webm`, `ogg` |
| Video | 500 MB | `video/mp4`, `webm`, `quicktime` |
| Export | 1 GB | `application/zip` (server-generated only) |

- **Per-profile storage quota** (suggested start: 5 GB), enforced at presign
  time against `SUM(byte_size)`. Without a quota, storage cost is unbounded.
- **Allow-list, never deny-list.** Anything not listed is rejected.
- Size is validated at presign (declared) **and** at complete (actual, via HEAD)
  — a client can lie about the first.

---

## 7. Validation and safety

- **Content type is verified server-side by magic bytes** at the complete step,
  not trusted from the client header. A `.png` that is actually an executable is
  rejected and the object deleted.
- **Executables and scripts are rejected outright** (`.exe`, `.dll`, `.sh`,
  `.bat`, `.js`, `.html` as uploads — HTML because a signed URL could otherwise
  serve attacker-controlled markup).
- **`Content-Disposition: attachment`** and `X-Content-Type-Options: nosniff`
  on download responses, so nothing renders inline in the browser origin.
- **Malware scanning:** not in v1. R2 has no built-in scanner. For a
  single-user app the realistic risk is low, and the honest position is to
  record it rather than pretend. If Life OS ever becomes multi-user, add
  ClamAV in a worker or a third-party scanning API **before** sharing is
  enabled. Flagged in the risk register.
- **Never execute, parse, or transform an uploaded file in the API process**
  beyond reading its header bytes.

---

## 8. Duplicate detection

The client computes a **SHA-256** before upload; the backend also verifies it at
completion.

- If `(profile_id, checksum_sha256)` already exists and is `ready`, the backend
  **returns the existing attachment** instead of a new upload URL, and simply
  links it to the new entity.
- This makes the same PDF attached to three projects cost one copy.
- De-duplication is scoped **per profile**, deliberately — sharing bytes across
  profiles would leak the existence of one profile's data into another and
  complicate deletion.

---

## 9. Thumbnails

- Generated **server-side after upload**, for images and video posters only.
- Sizes: `sm` 320px, `md` 768px (longest edge), WebP, quality ~80.
- Stored under the `thumbnails/` prefix; key recorded in
  `attachments.thumbnail_key`.
- Generated in a background job, never inline in the upload request. Missing
  thumbnails fall back to the original.
- Video thumbnails require ffmpeg; if that is unwanted on Railway, skip video
  posters in v1 rather than adding a heavy dependency.

---

## 10. Deletion and orphan cleanup

Two directions of drift are possible, so reconciliation runs both ways nightly:

| Case | Detection | Action |
|---|---|---|
| **Row deleted, object remains** | soft-deleted `attachments` older than 30 days | delete the R2 object, then the row |
| **Object exists, no row** | list bucket prefix, compare to `attachments` | delete after a 24-hour grace (protects in-flight uploads) |
| **Row `pending` >24 h** | status query | mark `orphaned`, delete any object |
| **Entity deleted** | `entity_id` no longer resolves | soft-delete the attachment |

- Deletion is **soft first** (30-day grace), so a mistaken delete is
  recoverable — consistent with the Postgres soft-delete policy.
- Deleting a **profile** enqueues a prefix deletion for
  `users/{userId}/profiles/{profileId}/`.
- Every deletion is logged with the object key and the reason.
- **R2 versioning is not relied upon**; the grace period is the recovery
  mechanism, which keeps costs predictable.

---

## 11. Metadata

Held in Postgres (`attachments`), never only in R2 object metadata:
`original_filename`, `content_type`, `byte_size`, `checksum_sha256`, `status`,
`entity_type`/`entity_id`, `thumbnail_key`, `metadata` jsonb (image
width/height, video/audio duration, page count).

A small set is *also* written as R2 custom metadata (`attachment-id`,
`profile-id`) purely to make orphan reconciliation possible from the bucket
side.

---

## 12. Exports and backups in R2

**User exports** (`life-os-exports`) — created by a job, delivered by a
short-lived signed URL, auto-expired after 7 days. Contents: `manifest.json`
(schema version, counts, generated-at), `data.json`, Markdown/HTML for Library
books and diary entries, CSVs for tasks/habits/reminders, and either the
attachment bytes or a manifest of them when the bundle would be too large.

**Backups** (`life-os-backups`) — nightly `pg_dump`, plus a pre-run snapshot
before every migration step (referenced by `migration_runs.backup_ref`), plus
the protected Firestore export retained for the whole rollback window.
**Backups are never mixed with user content**, and restore rehearsals happen in
staging (see `backend-architecture-v2.md` §14).

---

## 13. Lifecycle rules

| Prefix / bucket | Rule |
|---|---|
| `life-os-exports/**` | delete after **7 days** |
| `life-os-backups/**` | daily 7d · weekly 4w · monthly 6m |
| `**/thumbnails/**` | delete with the parent attachment |
| incomplete multipart uploads | abort after **24 hours** |

---

## 14. Migration of files

There is **nothing to migrate** — the app stores no files today. This is
greenfield, which is a rare piece of good luck in this project.

The only related concern is **notebook content**: cells hold raw HTML which
*could* contain a pasted `data:` image URL, inflating the Firestore record. If
any are found during migration, they are extracted to R2 and replaced with an
attachment reference. The migration step must scan for `data:image` in page
content and report counts before writing.

## 15. Credentials and environment

```
R2_ACCOUNT_ID
R2_ACCESS_KEY_ID
R2_SECRET_ACCESS_KEY
R2_BUCKET                 = life-os-prod
R2_BUCKET_EXPORTS         = life-os-exports
R2_BUCKET_BACKUPS         = life-os-backups
R2_ENDPOINT               = https://<account>.r2.cloudflarestorage.com
R2_PRESIGN_UPLOAD_TTL     = 900
R2_PRESIGN_DOWNLOAD_TTL   = 300
R2_MAX_UPLOAD_BYTES       = 524288000
R2_PROFILE_QUOTA_BYTES    = 5368709120
```

- **Server-side only.** Never shipped to the client, never in `config.js`.
- Use a **scoped R2 API token** limited to these buckets — not an account-wide
  key.
- Separate credentials for staging and production.
- Rotate on any suspicion; rotation must not require a code change.

**Requires user setup** (see the report): a Cloudflare account, three R2
buckets, one scoped API token, and lifecycle rules. **Not to be provisioned
without explicit authorisation.**
